# Application audit, November 10, 2026

The review covered transaction confirmation, amount entry, query identity and failure handling, portfolio summaries, validator selection, and responsive navigation. Findings below were reproduced in regression tests or the local production UI. This was an application review, not a smart-contract security audit.

## Fixed findings

| Impact | Cause | Change |
| --- | --- | --- |
| High: reverted EVM and Klip transactions could appear successful | Receipt completion was treated as success without checking its status; a missing client could bypass confirmation | Require a successful receipt, reject cancellation and replacement, accept successful fee repricing, and fail explicitly when confirmation is unavailable |
| High: malformed amounts could crash reward splitting or silently lose precision | Amount parsing concatenated unchecked input, truncated excess decimals, and returned an empty string for zero | Validate decimal syntax and precision, return canonical zero, reject invalid submissions, preserve exact unstake/redelegate MAX values, and reject amounts above the delegated balance |
| Medium: history could briefly show another account or chain | Previous query data was retained across identity changes and page state survived those changes | Scope placeholders to one account and chain, reset pagination by identity, disable pagination during placeholder loading, and show query failures with retry |
| Medium: portfolio showed invented historical growth | The chart generated a synthetic upward series from the current balance | Replace it with current validator/pool allocation calculated from actual delegations |
| Medium: failed reads appeared as empty balances or stale validators | Components ignored query errors | Show explicit unavailable states in overview summaries, validator lists, unbonding, allocation, and history |
| Medium: mobile navigation stayed open after selecting a destination | Link activation did not control the drawer state | Close the controlled drawer on navigation; verified at a 423px viewport |
| Medium: mobile header controls overlapped | Token price, menu, theme, and wallet controls shared one fixed-height row | Put token information on a separate mobile row; add accessible theme-control labels |
| Low: pie colors did not match the legend | Filtering empty chains changed the slice color index | Assign colors before filtering |
| Low: Sei yield was mislabeled and validator search was incomplete | Generic APY labeling and name-only search | Label Sei yield APR, search validator addresses, and return zero for equal voting power when sorting |

## Verification

- `node --test scripts/*.test.mjs`: 258 tests passed, including added regressions. The new failures were reproduced before the corresponding fixes.
- `pnpm build`: production compilation, TypeScript validation, and route generation.
- `pnpm lint`: no errors; the existing unused `unoptimized` warning in `scripts/wallet-view.test.mjs` remains.
- `git diff --check`: no whitespace errors.
- Local production browser checks: disconnected Overview and Portfolio, XPLA Stake navigation, the mobile drawer opening and closing after a destination is selected, and the corrected header without overlapping controls at 423px.

The transaction tests execute the real hook/helper code with simulated wallet and receipt responses. No funded wallet was connected, no transaction was signed, and no deployment was performed. Connected-account error states and amount dialogs were exercised with component/hook tests rather than funded browser sessions.

## Remaining limits

The local environment has no usable WalletConnect project configuration. The browser reported missing Cosmos mobile `walletconnectOptions` and rejected requests made with the EVM fallback project ID. End-to-end mobile wallet connection requires valid project configuration; this review did not provision credentials or claim those connections work.

New liquid-staking provider positions are still not consolidated into the shared Portfolio/Overview totals. Their provider-specific views remain the source for those positions. This existing coverage gap requires a separate portfolio data integration, rather than assuming native delegation totals include liquid holdings.
